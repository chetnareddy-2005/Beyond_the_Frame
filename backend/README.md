# Backend API (Phase 6)

The backend serves the frozen research outputs under `results/caltech_rgb_tracking` through its legacy API, and can create isolated dynamic video runs under `results/dashboard_runs`. Dynamic runs never write into the historical experiment directories.

The historical Phase 5 CSVs are frozen experiment artifacts. Backend startup
validates their schemas, track consistency, score ranges, and modality status;
it does not require Phase 5 results generated by the current implementation to
match historical baseline confidence values. Current pipeline outputs may
legitimately differ from those frozen values.

## Runtime

The HTTP server uses Python's standard-library `http.server`, but the full
application is not standard-library-only: video decoding, image processing,
detection, and tracking require the packages in the root `requirements.txt`,
which delegates to the bundled detector's `requirements.txt`. PyTorch
CPU/CUDA wheel selection is host-specific; see the root README for setup.

From the project root, start the server with:

```powershell
python -m backend.server
```

It listens on `http://127.0.0.1:8000` by default. Set `BTF_PROJECT_ROOT` or pass `--project-root` to point to another project checkout. The default project root is resolved relative to this backend package. Use `--host` and `--port` to change the bind address.

## Read-only endpoints

- `GET /api/auth/session` (public session status)
- `GET /api/health`
- `GET /api/overview`
- `GET /api/tracks`
- `GET /api/tracks/{track_id}`
- `GET /api/tracks/{track_id}/evidence`
- `GET /api/tracks/{track_id}/vlm`
- `GET /api/tracks/{track_id}/modalities`
- `GET /api/tracks/{track_id}/fusion`
- `GET /api/modalities`
- `GET /api/fusion/summary`

Except for health and session status, API requests require an authenticated session. Unknown tracks return a structured 404. Invalid track IDs or unsupported query parameters return a structured 400. Selected crop references are checked to remain within the Phase 4 RGB evidence directory and are returned as relative paths.

## Authentication

The backend creates its first user only when credentials are configured. A fresh
installation must set a bootstrap username and password before the server starts;
no default admin account is silently created.

Set either environment variables or the equivalent CLI arguments before startup:

```powershell
$env:BTF_AUTH_USERNAME = "demo-admin"
$env:BTF_AUTH_PASSWORD = "replace-me-with-a-strong-password"
python -m backend.server
```

Or:

```powershell
python -m backend.server --auth-username demo-admin --auth-password "replace-me-with-a-strong-password"
```

A legacy development-only fallback is available only when explicitly enabled:

```powershell
$env:BTF_ALLOW_DEVELOPMENT_DEFAULTS = "1"
```

This uses the historical local demo account (`Admin@beyondtheframe` /
`admin@123`) only for non-production local testing and is intentionally not a
production default. The password is stored as a salted PBKDF2-HMAC-SHA256 hash
in the separate
`results/auth/users.sqlite3` database; analysis and run data stores are not used
for user records. The backend issues an HTTP-only, `SameSite=Strict` session
cookie for an in-memory server-side session. Sessions expire after eight hours and
are invalidated at logout or when the backend restarts. The dashboard proxy
forwards the cookie between the browser and backend. `/api/health` and
`/api/auth/session` are public; protected API requests return HTTP 401 when
there is no valid session. Set `BTF_COOKIE_SECURE=1` when serving the dashboard
over HTTPS.

Authentication endpoints:

- `POST /api/auth/login` — JSON object containing `username` and `password`;
  invalid or empty credentials return the same generic HTTP 401 response.
- `POST /api/auth/logout` — invalidates the current session and expires its
  cookie.
- `GET /api/auth/session` — returns whether the request has a valid session.
- `GET /api/auth/history` — returns the authenticated user's persisted login
  and logout times and session duration. Session history contains no cookie or
  credential data.

## Dynamic runs

Upload a video as the `video` field in a `multipart/form-data` request:

```powershell
curl.exe -F "video=@datasets/videos/V_DRONE_005_square.mp4" http://127.0.0.1:8000/api/runs
```

The response provides a server-generated run ID and `queued` status. Start
processing with `POST /api/runs/{run_id}/start`, and poll
`GET /api/runs/{run_id}` for the persisted stage/status/progress. The default
upload limit is 250 MiB; set `BTF_MAX_UPLOAD_BYTES` to a positive byte count to
change it. Supported filename extensions are `.mp4`, `.avi`, `.mov`, and
`.mkv`; filenames are never used as storage paths.

## Phase 2 input preparation

The authenticated dashboard first selects an input source. CCTV is the live
RTSP branch; Upload Video then requires an RGB, Thermal, or Radar data type.
`POST /api/input/prepare` validates and prepares inputs without starting the
analysis pipeline.

For RGB or Thermal, send a `multipart/form-data` request with `source=upload`,
`input_type=rgb|thermal`, and exactly one file field named `file`. RGB and
Thermal currently use the existing `.mp4`, `.avi`, `.mov`, and `.mkv` video
containers. The backend checks the safe filename, size, and non-empty payload,
opens and decodes a frame, and returns metadata plus a prepared `run_id`.
Thermal decoding reuses `multimodal.thermal_adapter.ThermalAdapter`; no
Thermal detector or fusion is run.

Radar preparation returns HTTP 415 (`unsupported_radar_format`) because the
project does not define a user-uploadable Radar file format. The isolated
BOREAS research code consumes devkit-loaded Radar scans and is not a generic
upload parser.

For CCTV, send JSON with `source=cctv`, `action=test|start`, and `rtsp_url`.
Only `rtsp` and `rtsps` URLs are accepted. `test` opens, reads one frame, and
releases the stream. `start` opens and reads a validation frame, then keeps the
capture available until `POST /api/input/cctv/stop`, logout, observed session
expiry, or backend shutdown. Open/read timeouts are set to five seconds.
Responses and persisted input state contain only the RTSP origin; embedded
credentials, path, and query are not saved or returned.

A successful `start` returns a `READY_FOR_PHASE_3` handoff with
`source_type=cctv`, `input_type=null`, `live_reference_id`,
`connection_status`, `frame_available`, and frame dimensions. It does not
report a real-time FPS. The authenticated
`GET /api/input/cctv/{live_reference_id}/handoff` returns the current handoff
descriptor, and `GET /api/input/cctv/{live_reference_id}/frame` obtains the
current frame as JPEG with `X-Input-Source`, `X-Live-Reference-ID`, and
`X-Frame-Available` headers. Backend consumers can use
`InputPreparer.get_current_cctv_frame(user_id, live_reference_id)` to obtain a
copy of the current decoded frame and its handoff metadata. A stopped, expired,
or otherwise invalid reference cannot provide frames. This boundary does not
start or invoke any Phase 3+ processing.

## Phase 3 frame preparation

`backend.frames` defines the `PreparedFrame` contract and
`Phase3FrameManager.acquire_next(...)` source-neutral acquisition interface.
Authenticated `POST /api/phase3/frame` accepts the selected source and either a
prepared `run_id` or CCTV `live_reference_id`. It returns one validated,
contiguous image frame encoded as JPEG/base64 plus source metadata and
validation/preprocessing statuses. For uploads, `end_of_video` is true when
sequential acquisition reaches EOF. `POST /api/phase3/stop` releases an active
upload reader.

RGB acquisition reads sequentially from the safely resolved stored file,
tracks zero-based frame indexes, validates each decoded array, and releases
the capture on EOF, error, logout, session expiry, run start, or shutdown.
General Phase 3 preprocessing copies validated arrays into contiguous memory;
detector-specific letterboxing, tensor conversion, and scaling remain in the
existing detector path.

CCTV acquisition reuses the Phase 2 capture owner and its live reference.
Thermal acquisition reuses `ThermalAdapter` and yields normalized grayscale
`uint8` intensity frames; those values are not calibrated temperature data.
Neither source invents timestamps or frame indexes. Radar remains blocked
because there is no supported dashboard upload format. Producing a prepared
frame does not invoke the detector or any later pipeline stage.

## Phase 4 single-frame object detection

Authenticated `POST /api/phase4/detect` obtains exactly one `PreparedFrame`
through `Phase3FrameManager.acquire_next(...)` and passes it directly to the
Phase 4 `DetectionService`. RGB uploads and visible-light CCTV use
`artifacts/checkpoints/best.pt`. Thermal uploads use the separate
`artifacts/checkpoints/thermal_bird_drone_best.pt` checkpoint and require its
class mapping to be exactly `0=Bird`, `1=Drone`; thermal and RGB runtimes are
cached independently. Radar remains unsupported.

The RGB checkpoint is overridable by `BTF_DETECTOR_WEIGHTS`; the thermal
checkpoint is independently overridable by `BTF_THERMAL_DETECTOR_WEIGHTS`.
Each selected YOLOv5 `yv5_gh` checkpoint must contain the custom GhostNet and
AFNO2D architecture; startup rejects weights that lack GhostConv,
GhostBottleneck, or AFNO2D modules.
the service uses the existing 640-pixel image size, 0.25 confidence threshold,
and 0.45 NMS IoU threshold. Detection and SmolVLM independently select CUDA
when PyTorch reports it available and otherwise use CPU. Detector preprocessing uses
the repository's YOLOv5 letterbox, BGR-to-RGB, HWC-to-CHW, contiguous-array,
float normalization, and batch conversion helpers. Thermal frames are
normalized grayscale intensity `uint8` images (not temperature-calibrated);
they are expanded to three identical channels for the model and letterboxed
without changing their intensity values.

The response contains a normalized per-frame `DetectionResult`, an annotated
JPEG preview, model/inference metadata, and no track, temporal, reliability,
VLM, or final-decision fields. The endpoint runs only inference, confidence
filtering, NMS, and bounding-box validation; it does not start the existing
full analysis runner or own the Phase 3 frame source. The detector instance is
closed during backend shutdown.

## Phase 5 single-frame object tracking

Authenticated `POST /api/phase5/track` obtains the next Phase 3 prepared frame,
passes it through the unchanged Phase 4 `DetectionService`, and adapts the
result to the existing `supervision.ByteTrack` implementation. RGB and
Thermal uploads retain separate per-run tracker state; Thermal uses the
Bird=0, Drone=1 detector mapping. Visible-light CCTV remains RGB-only. The returned
`TrackResult` contains only source/frame metadata and tracked object IDs,
classes, confidences, and bounding boxes. Repeated requests for the same run or
live CCTV reference reuse the same in-memory tracker; source changes, explicit
reset, stop, end-of-video, logout, and backend shutdown clear the relevant
tracker state. `POST /api/phase5/reset` explicitly resets the authenticated
session's tracker.

## Phase 6 temporal analysis

The dashboard forwards each authenticated Phase 5 `TrackResult` to
`POST /api/phase6/temporal`. This separate boundary adapts the observations
into the existing `TrackletMemory`, `compute_temporal_features`, and
`compute_track_trajectory` implementations. It returns per-track temporal
summaries, class history, image-plane motion summaries, and trajectory points;
it does not call the detector or tracker and does not persist temporal state
to the database.

Temporal history is held in memory per authenticated session and input source.
Explicit Phase 5 reset, input stop/change, logout, session expiry, and backend
shutdown clear it. For RGB uploads, source frame indexes and validated video
FPS provide frame/timing context when available. CCTV uses the Phase 5 observation sequence index only; no camera timestamp,
frame rate, real-time speed, or physical-world calibration is claimed.
Thermal single-frame temporal analysis and Radar tracking remain unsupported;
single-frame Thermal tracking stops at Phase 5 and does not invoke Phase 6.
Full-video Thermal runs use a separate offline track-consensus stage after
detection/tracking; this does not activate the interactive Phase 6 endpoint.
An RGB upload end-of-video notification finalizes and clears its temporal history.

The Phase 4 `/api/phase4/detect` endpoint remains detection-only. Phase 5 does
not invoke temporal analysis, reliability, VLM, evidence fusion, or reporting,
and it does not persist tracker state to the database.

Uploaded input state is added to the existing per-run JSON manifest and status
file with `source_type`, `input_type`, `input_status`, `input_metadata`, and a
safe relative `input_reference`. CCTV connection state is written separately
under `results/dashboard_runs/input_states/` without RTSP credentials.

Prepared RGB and Thermal runs remain in `prepared` status until the existing
explicit `POST /api/runs/{run_id}/start` action is requested. RGB continues
through the existing full analysis pipeline. Thermal uploads use sequential
full-video detection/tracking: each decoded frame passes through
`ThermalAdapter.preprocess_frame`, the configured Bird=0/Drone=1 thermal
checkpoint, and the existing ByteTrack service. The run stores
`tracking/detector/tracks.csv`, a detector manifest, status/progress, and
`final_results.json`; the one-based run frame and zero-based decoder index and
capture timestamp are retained separately.

Thermal runs compute offline, run-level temporal consensus after frame
processing from the persisted detector/tracker observations. It writes
`temporal/temporal_consensus.csv` and
`temporal/temporal_consensus_manifest.json`, reports real per-track progress,
and leaves raw observations unchanged. The offline decision is heuristic,
uses the complete track (including later frames), and is not suitable as a
causal/live decision or an accuracy claim. Its decision score is not a
calibrated probability. Reliability, evidence selection, VLM, fusion,
and assessment remain `skipped`/`not_run`. A completed Thermal run may report a
detector-only `REVIEW` cue when its persisted tracks contain a Drone prediction;
its representative evidence points to an observation in that run's tracking
CSV. This is unverified model output, not an independently validated or
operational alert. Detector class predictions are not ground-truth labels.
Thermal runs cannot use the RGB detector-checkpoint resume path. Existing
legacy `/api/runs` uploads and RGB start behavior remain available.

Run results are available at:

- `GET /api/runs/{run_id}/overview`
- `GET /api/runs/{run_id}/tracks`
- `GET /api/runs/{run_id}/tracks/{track_id}`
- `GET /api/runs/{run_id}/tracks/{track_id}/evidence`
- `GET /api/runs/{run_id}/tracks/{track_id}/vlm`
- `GET /api/runs/{run_id}/tracks/{track_id}/modalities`
- `GET /api/runs/{run_id}/tracks/{track_id}/fusion`
- `GET /api/runs/{run_id}/fusion/summary`
- `GET /api/runs/{run_id}/evidence/{relative_image_path}`

Each run has a separate generated directory, manifest, status file, input,
stage outputs, and evidence. Run result APIs return 409 until processing has
completed; unknown/malformed IDs return 404/400. Evidence serving is restricted
to image files resolved under that run's evidence directory. A restart marks
interrupted `processing` runs failed rather than silently resuming them.

The runner reuses the existing detector/tracker CLI, temporal/reliability
functions, selective-evidence functions, and Phase 5 fusion function. The
default detector checkpoint is `artifacts/checkpoints/best.pt` within the
project. Set `BTF_DETECTOR_WEIGHTS` to override it. A missing selected checkpoint
fails the dynamic run explicitly; no developer-home fallback is used. The RGB
checkpoint is loaded in an isolated detector process with a local compatibility
shim for legacy Windows `pathlib._local` checkpoint references. Each run
manifest records a logical checkpoint name and SHA-256, detector architecture
and settings, preprocessing description, source-video SHA-256, and available
video FPS and dimensions; it does not record a machine-specific checkpoint
path. Detection uses 640-pixel input, confidence threshold 0.25, NMS IoU 0.45,
and the automatically resolved CUDA or CPU device. Detection and CPU processing
can take a long time. Only one dynamic run may process at a time.

Thermal runs instead use `artifacts/checkpoints/thermal_bird_drone_best.pt`
and `BTF_THERMAL_DETECTOR_WEIGHTS`; the detector validates the checkpoint's
Bird=0, Drone=1 class order and custom YOLOv5 + GhostNet + AFNO2D model.
Sequential thermal processing applies per-frame grayscale conversion and
min/max intensity normalization; this is not temperature calibration.
Completed thermal track-detail responses include a versioned `evidence_ledger`
derived from the run's persisted `tracks.csv` and detector manifest. It links
back to the existing per-frame observations instead of storing duplicate
images or a second observation database, and records predicted class changes,
unobserved intervals, raw detector confidence, and checkpoint provenance.
Track-level temporal consensus is persisted separately and exposed with its
reason codes, supporting/contradictory predicted frame references, algorithm
version, and heuristic-score interpretation. Those references are model
outputs, not human-verified labels. Image-quality indicators and independent
supporting/contradictory frame labels remain unavailable; selective
verification remains not run for thermal runs. Older runs without the
consensus artifact expose a derived-on-read result separately from a persisted
run-stage artifact. Failed or still-processing runs with persisted observations
are marked `partial`.

CPU-only machines can use the standard CPU-compatible PyTorch installation.
For NVIDIA acceleration, install a PyTorch build compatible with the machine's
CUDA driver using the official PyTorch installation selector; the application
does not pin or install NVIDIA-specific packages.

Dynamic runs currently skip automatic SmolVLM inference for every track. The
run writes an empty, schema-valid VLM results file and reports
`vlm_status: "skipped"`; detector/temporal labels are therefore unverified.
The VLM adapter remains available for explicit use, but it is not part of the
default dynamic-run path. The assessment field is `MANUAL_REVIEW`; it is not an
operational threat determination.

Run status includes a separate `vlm_status`: `pending`, `processing`,
`completed`, `skipped`, or `unknown`. A VLM completion transition is accepted
only when the run-scoped `vlm_results.csv` contains at least one result row.
Older persisted runs without this status are shown as uncertain rather than
being inferred complete from the overall run status.

Dynamic reliability outputs retain the existing `motion_score`, default
weights, and `reliability_score` unchanged. They additionally include a
`legacy_motion_score` alias and an optional `trajectory_motion_score` with
image-plane metric components derived from that run's motion summary. This is
diagnostic evidence only and does not enter the reliability score or status
decision. Historical reliability artifacts and outputs are not rewritten.

This backend is a local prototype, not a public upload service. Keep it bound
to loopback; authentication does not replace deployment isolation, HTTPS,
resource controls, or changing the demo credentials. Processing runs can be
cancelled through the dashboard/API; thermal processing checks for cancellation
between decoded frames. A run cannot be started twice.

VLM confidence is explicitly identified as a generation-token probability proxy, not calibrated probability. Reliability is identified as heuristic. For Thermal and Radar, unavailable or unestablished associations are represented as `null` plus a status rather than as negative detection evidence. Track 24 reports synchronized Thermal frames but no validated spatial association; radar-to-Caltech synchronization and track association remain not established.

Track API `source` fields preserve the field name but expose only the source
video filename; local absolute machine paths are not returned. Uploaded
original filenames are replaced with generated names before storage.

Run-scoped routes enforce the authenticated account's run ownership. Stored
source video is available through `GET /api/runs/{run_id}/video`, including
single byte-range requests for browser seeking. `GET
/api/runs/{run_id}/reuse-candidates` finds completed results with the same
source-video SHA-256; those results are view-only and are never merged into a
new run. `POST /api/runs/{run_id}/reanalyze` creates a distinct prepared run
from the stored RGB input, leaving the original run unchanged.

During RGB and thermal video inference, detector/tracker observations are
flushed to the run's `tracking/detector/tracks.csv` as each frame completes.
After a Drone-labeled track persists across three consecutive frames,
`GET /api/runs/{run_id}/early-alert` can return a **provisional review** cue
while the remaining analysis stages continue. It is explicitly unverified and
does not indicate a friendly/hostile identity. Final fusion resolves the same
candidate as `confirmed_review` or `not_confirmed`; a failed/cancelled run is
reported as interrupted rather than leaving a provisional cue looking final.
The alert cue improves notification timing; it does not make CPU video analysis
run at the video's frame rate.

For failed or cancelled uploads, `GET
/api/runs/{run_id}/resume-checkpoint` reports whether a safe detector/tracker
checkpoint is available. `POST /api/runs/{run_id}/resume` creates a new run
only when detection and tracking completed, `tracks.csv` passes schema/value
validation, the checkpoint manifest belongs to the selected run, the
source-video and detector configuration hashes still match, and the checkpoint
contract version is current. The new run copies only the validated tracking
CSV and detector manifest; it reruns temporal analysis and all later stages.
Unvalidated or incompatible checkpoints are refused, and fresh analysis
remains available. Backend restart still marks interrupted workers failed; it
does not resume them automatically.

## Authorized drone simulation (Phase 10)

The authenticated dashboard route `/authorization` exposes a simulation-only sector registry. `GET /api/authorization/simulation` returns the signed-in account's configured rectangle/grid plus synthetic registry/demo telemetry. `POST /api/authorization/config` saves that account's rows, columns, and latitude/longitude bounds to `results/authorization/settings.sqlite3`. Rows and columns are limited to 1–8, with at least two total sectors. `POST /api/authorization/evaluate` checks a demo or supplied telemetry point against the current account's layout and permission window.

The registry entries and displayed locations are synthetic constants; only the sector grid is saved per account. This is not a production registry or live GPS integration. A non-match, missing GPS, expired permission, or sector mismatch is a review state and never a hostile classification. The dashboard uses a local SVG grid, not Google Maps or another map tile provider.
