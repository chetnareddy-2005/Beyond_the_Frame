# Phase 2 — Requirements and test scenarios

**Checkpoint date:** 2026-10-22  
**Status:** Requirements and acceptance criteria are frozen as of 2026-10-22. Eligible held-out V1/V2 videos, reviewed labels, and a sequence-level test split are not locally available; those are data-readiness dependencies for later phases, not reasons to weaken this frozen specification.

## Scope boundary

The system makes two separate assessments:

1. **Visual class:** Bird, Drone, or Uncertain, based on image/video evidence.
2. **Authorization:** Authorized match, Unknown / Needs review, or Permission mismatch, based on a trusted ID and a permission record.

The detector cannot determine whether a drone is friendly or hostile from appearance alone. The UI and reports must not call a drone “rogue” without verified authorization evidence. A possible visual Drone result is an unverified review alert, not a confirmed threat.

## Shared data and evaluation rules

- Keep original videos immutable. Record source, license/access terms, file hash, dimensions, FPS, frame count, and annotation version for each evaluation clip.
- Store per-frame boxes as `x1,y1,x2,y2`, class, sequence-scoped ground-truth object ID, visibility/occlusion note where available, and frame index. Confirm box coordinates against the original frame before use.
- Keep an entire source sequence in exactly one of train, validation, or test. No frames from one sequence may cross those splits. The four SMOT4SB pilot sequences are from its training partition; they are development material, not an independent final test set.
- Compare detections to labels with one-to-one matching at IoU ≥ 0.50, and report per-class precision, recall, and AP50/AP50:95. Also show results by object-size bin because distant objects are very small.
- Evaluate tracking with IDF1 and HOTA (or a clearly named equivalent), ID switches, fragmentation, and track coverage. Do not treat detector-only misses as tracker failures; report detector and oracle-GT tracker runs separately.
- Match predicted IDs to ground-truth IDs by an evaluation assignment. The numeric ID generated by the application does not need to equal the annotation ID; it must remain unique and consistent for the same object within the run.
- Record alert false positives, missed drone alerts, alert frame/time, first supporting detection frame/time, and whether the linked evidence frame belongs to the same track.

## Additional stress cases

- **Small/far target:** retain native-resolution GT box sizes and report metrics in `<16 px`, `16–32 px`, and `>32 px` longest-side bins. These bins are descriptive; report performance rather than assuming every tiny object is detectable.
- **Temporary occlusion or missed detection:** include naturally occurring gaps where possible, record gap length in frames, then report whether the same GT identity is reacquired or fragmented. Evaluate at short, medium, and longer gaps (for example 1–5, 6–15, and >15 frames) if the dataset supports them.
- **Thermal:** evaluate independently from RGB using thermal-specific labels/checkpoints. Report track IDs and image-plane trajectory in pixels; state that pixel movement is not physical distance and image intensity is not calibrated temperature unless calibration data exists.
- **Unknown drone ID / authorization:** use simulated registry cases until a trusted real ID source is approved: authorized and in-area/in-time; ID absent; permission expired; and out-of-area. Visual class remains Drone in all drone cases. Authorization state must be separate; absent ID means **Unknown / Needs review**, never automatically rogue.

## Dashboard consistency checks

For every completed run:

1. Each alert displays its track ID, evidence frame/time, visual class, confidence, and review reason.
2. “Total tracks” is the count of distinct track IDs. Bird, Drone, and Uncertain counts are per-track counts and reconcile to the total (with any unclassified category shown explicitly).
3. Alert count is not expected to equal total track count: bird tracks should not create UAV alerts, and uncertain tracks may be review-only. The UI must label these counts so users do not confuse them.
4. Selecting an alert/evidence frame and selecting that track in the trajectory view refer to the same track/run.
5. Display detection/evidence time separately from alert creation time. If frame-to-time mapping is approximate, disclose that.

## Change control for this frozen specification

- Treat this document as acceptance-specification version **1.0**, frozen on 2026-10-22.
- Do not change thresholds, expected classes, alert rules, or summary rules after viewing evaluation results just to make a result pass.
- If project requirements genuinely change, create a new version with the reason, date, and affected scenarios recorded before evaluating those scenarios. Preserve this frozen copy and identify which spec version each result used.
- Missing data does not waive or redefine a scenario. Report it as **not evaluated / future data required**.
